# ADR-0004 — Idiomatic C# core plus `By*` façade, with parameter-type-sequence dedup for node generation

**Status:** Accepted
**Date:** 2026-08-27
**Deciders:** Nicety

## Context

Spark has two audiences for the same API. A .NET developer writing C# inside a code block
expects `new Circle(centre, radius)`. An AEC user coming from Dynamo or Grasshopper reads
`Circle.ByCenterRadius(centre, radius)` and knows immediately what it does; D9 makes AEC
the tie-breaker in any direct UX conflict. `C2VGeometry`'s `VCoordinateSystem` already
carries the `By*` naming template, so the style is not foreign to the harvested code.

Supporting both is easy at the language level and dangerous at the node level. Nodes are
generated by reflection over public members, so a type with both a constructor and a
matching factory emits two nodes that do the same thing with different names. Across a
kernel this doubles the library and makes search results untrustworthy.

The failure mode to avoid is already documented in this codebase. `DoodleSharp`'s
`DocGenerator` is 6,784 lines around three hand-maintained dictionaries — roughly 1,478
member descriptions keyed by string — which needed two dedicated test suites to stay honest,
and even then 101 of 108 public constructors were found rendering blank while 7 carefully
written entries pointed at members that no longer existed. Any solution here that relies on
a hand-maintained list of exceptions will decay the same way.

## Decision

Both forms exist in the public API. `Spark.Geometry` is written as idiomatic C# with real
constructors, and a `By*` façade of public static factories sits alongside.

For node generation, the importer suppresses a constructor when a public static
`By*`/`From*`/`Create*` method on type `T` returns `T` and its **parameter type sequence**
matches that constructor's. `new Circle(c, r)` and `Circle.ByCenterRadius(c, r)` therefore
collapse to a single node. Anything a factory does not cover still emits its constructor, so
no member becomes unreachable.

This is enforced by a two-way reflection test: every public member resolves to exactly one
node or is listed in an exclusions file with a stated reason, and every generated node
resolves to a live member. It is the `DocumentationAccuracyTests` lesson applied
prophylactically rather than after the damage.

Because ADR-0016 removes any Dynamo compatibility obligation, the `By*` names carry no
semantic contract with ProtoGeometry. They are for human recognition only.

## Alternatives considered

### `By*` factories only, no public constructors

One node per construction falls out for free, and it matches what AEC users already read.
It lost because it makes the library unidiomatic for the C# code block, which is the
project's signature feature — a developer typing `new Circle(` and finding nothing is a bad
first impression of a .NET-native tool — and because it would put the kernel's public shape
at odds with the whole NuGet ecosystem it is meant to sit inside.

### Constructors only

Purest C#, and the node names would be generated mechanically as `Type.ByParamNames`.
It lost on recognition: overloaded constructors give the node generator nothing to
disambiguate with beyond parameter names, and the resulting library reads as a type list
rather than as a catalogue of operations. D9's AEC-first tie-break settles it.

### Suppress duplicates with an attribute on each constructor

Explicit and free of heuristics; a reviewer can see exactly what is hidden. It lost for two
reasons. It is a hand-maintained mapping between members, which is precisely the
`DocGenerator` failure shape. And zero-config reflection over third-party packages must
produce a sane library with no attributes at all, so the importer needs a rule that works
without cooperation from the library author.

### Deduplicate by parameter *names* rather than types

Slightly more precise where two constructions share a shape but mean different things.
It lost because innocuous naming differences — `center` against `centre`, `c` against
`origin` — would fail to match and emit both nodes, which is the exact outcome the rule
exists to prevent.

## Consequences

### Positive

One node per construction, with the library search index and the help node-coverage check
both operating on a set with no synonyms in it. Third-party packages get the same treatment
with no attributes required. The two-way test makes an unreachable or dangling node a build
failure.

### Negative

The heuristic can suppress a constructor whose semantics genuinely differ from a factory
with the same parameter type sequence — two `double`s meaning radius and height in one and
width and height in the other. The exclusions file is the escape hatch, and it must carry a
reason, but every entry in it is a small piece of the hand-maintained list this decision was
supposed to avoid. Both forms also need XML doc comments, since ADR-0015 makes CS1591 an
error on `Spark.Geometry`.

### Neutral

Overloads remain one node each, grouped under a single library entry with a flyout and
disambiguated by differing parameter names rather than numeric suffixes.

## Notes

If the exclusions file grows past a page, that is the signal that the type-sequence rule is
too blunt and the dedup rule itself should be revisited — not that more exclusions should be
added.
