# ADR-0019 — Deliberate change control on `Spark.Api` and `Spark.Geometry`, not permanent additivity

**Status:** Accepted
**Date:** 2026-08-27
**Deciders:** Nicety

## Context

ADR-0009 decided that `Spark.Api` and `Spark.Geometry` would be **strictly additive for the
whole of 1.x**. Its argument rested on a public package ecosystem: Spark's own contract
assemblies published to nuget.org, third-party node packages compiled against them, and a load
model in which contract assemblies always resolve from the default context. From those three
facts the conclusion followed cleanly — one breaking change would break every installed package
in the world simultaneously, with no per-package migration path — and the constraint was
accepted at M0 on that basis.

**The first of those three facts was a misread requirement.** The client's requirement is that
Spark *consumes* NuGet packages and loose DLLs, so a user can bring any .NET library into a
graph and get nodes from it — the equivalent of Dynamo's Package Manager. It was never that
Spark publishes its own assemblies as packages. Nothing in this repository is published to
nuget.org, `IsPackable` is `false` repository-wide with the reasoning in
[`Directory.Build.props`](../../Directory.Build.props), and [NOTES.md N14](../NOTES.md) records
the fact so it is not re-litigated. There is no published contract ecosystem for a breaking
change to fracture, and there will not be one.

Removing that premise does not empty the argument. What survives is smaller, and is stated here
at its true weight rather than at ADR-0009's:

- **A user's own custom node DLL is real.** Somebody compiles an assembly against `Spark.Api`,
  loads it into a graph, and upgrades Spark. A breaking change means they recompile. That is an
  annoyance for one person who holds the source, not a fracture across an ecosystem of packages
  whose maintainers may never return to them.
- **The geometry kernel is the foundation every other kernel type sits on.** Churn in
  `Spark.Geometry` is expensive regardless of who consumes it: per-type `schemaVersion`s move,
  golden files move, every node generated by reflection over it moves, and so does every help
  topic that names one. That cost is paid by us and by every user of the product, and it does
  not depend on packaging at all.
- **The load model is unchanged.** Consumed packages load into one collectible
  `AssemblyLoadContext` per package *version*, and **contract assemblies still always resolve
  from the default context**, because a `Circle` produced by one package must be the same `Type`
  as a `Circle` consumed by another or the two cannot be wired. That belongs to E7 and is not
  touched here. What changes is only what follows from it about versioning policy.

## Decision

`Spark.Api` and `Spark.Geometry` are under **deliberate change control proportionate to the
cost of the change**, rather than strictly additive by rule.

1. **Adding remains the first choice.** A new overload, a new interface, a new type. A change
   that can be expressed additively is expressed additively, and `[Obsolete]` plus a superseding
   member is still the normal way to retire a mistake.
2. **A breaking change is permitted within 1.x** when it is genuinely better than living with
   the mistake — but it is a decision with a record, never an edit made in passing. Say what
   breaks, say who has to recompile, and put it in the release notes before it ships rather than
   after somebody finds it.
3. **`Spark.Api` stays deliberately small.** This was always the stronger half of ADR-0009's
   design advice and it survives the correction untouched: `Spark.Api` is a contract, not a
   convenience library, and anything that can live in `Spark.Engine` does.
4. **Public-API baselines stay, and their purpose is restated.** They are a **review aid, not a
   compatibility guarantee**. Their value is that every public API change becomes a visible line
   in a diff, which is what stops a public surface growing by accident; they also remain the
   trigger for the `docs-freshness` CI job. Keeping them was never contingent on publishing.
5. **`Spark.Geometry` gets the tighter hand of the two**, on the foundation argument above — not
   on an ecosystem argument.

## Alternatives considered

### Keep ADR-0009 exactly as written

Its rule is mechanical, unarguable in review, and produces the smaller and more considered API
surface that ADR-0009 correctly named as a benefit. Nothing about it stops working when the
premise goes; it simply becomes expensive insurance against a risk nobody carries. It lost
because the cost is permanent and falls on users of the product: an awkward signature shipped in
`Spark.Geometry` at M1 would still be there at 1.9, still documented, still generating a node
beside its better-named replacement, and the node library and the generated reference would both
be longer and more confusing for it. Paying an ecosystem's insurance premium with no ecosystem
to insure is cost without benefit, and the honest response to discovering that is to say so.

### Withdraw the constraint entirely

Treat `Spark.Api` and `Spark.Geometry` as ordinary assemblies inside an application, changeable
like any other, and drop the public-API baselines with them. This is the position the corrected
premise most directly suggests, and it has the merit of removing a review chokepoint from every
API-touching pull request. It lost on the two reasons that genuinely survive — a user's custom
node DLL is a real artefact that a careless change breaks, and the kernel is the foundation
everything else is built on. It would also have discarded the baselines, which are worth keeping
for a reason unrelated to compatibility: an unreviewed public surface grows, and nothing else in
the build would notice.

### Delete ADR-0009 and rewrite it in place

Tidier to read, and it would leave one correct record where there are now two. It lost because
this set says plainly that records are written once and are not edited to reflect later opinion,
and this is precisely the case that convention exists for. Rewriting 0009 would also erase the
evidence of something worth keeping: a design constraint accepted at M0, before implementation,
on a requirement nobody had checked with the client. Supersession keeps the original argument
and the correction side by side, so the next person tempted to adopt a permanent 1.x-wide
constraint can read what happened the last time.

## Consequences

### Positive

A design mistake in the kernel can be fixed rather than deprecated and carried, so the public
surface stops accumulating parallel members by rule. `Spark.Geometry` in particular can be got
right during M1 to M6 — the milestones where its shape is still being discovered — instead of
being frozen at its first draft. The public-API baselines survive with a purpose that is
defensible on its own terms, which makes them harder to argue away later.

### Negative

**"Deliberate" is a judgement standard where "strictly additive" was a mechanical one**, and a
judgement standard is the weaker of the two under time pressure. There is now a decision to have
where previously there was a rule to point at, and the failure mode is a breaking change that
nobody argued about because everyone assumed somebody else had. A user with a custom node DLL
can be broken by a minor release and has to be told so in the release notes. PRD §10's
zero-breaking-changes success measure loses its crispness and becomes a judgement about whether
each break was worth it.

### Neutral

Records written before this correction lean on ADR-0009's stronger claim: ADR-0001, ADR-0003,
ADR-0005, ADR-0007, ADR-0008 and ADR-0010 all cite it. Where the softer claim is what was meant,
those citations now point here; where the citation is about the load model or about NuGet as the
package manager Spark consumes, it correctly still points at ADR-0009. Two are worth naming:

- **ADR-0007** rejected calendar versioning because "published contracts that people compile
  against" need a version number that answers *does upgrading break me?*. The published half of
  that is gone; the question is not. An embedder referencing `Spark.Host` from an install, and a
  node author with a DLL compiled against `Spark.Api`, both still need the answer, and SemVer
  still gives it. That decision now stands on a narrower base than it was argued on, and is left
  standing rather than rewritten.
- **ADR-0010**'s aside — that a `const` epsilon baked into a caller is "an ADR-0009 hazard hiding
  inside a constant" — still names a real hazard, now against a user's own compiled DLL. Its
  citation is left pointing at ADR-0009 because the same sentence appears as a comment in
  `src/Spark.Geometry/Tolerance.cs`, and the two should move together in a change that is
  allowed to touch source.

## Notes

The pressure-release valve ADR-0009 described is still the preferred route and not merely the
permitted one: introduce a new interface additively, obsolete the old one, leave it working. What
changes is that the alternative — decide the break is worth it, record it, and ship it in a
1.x release — is now available rather than forbidden. Reach for it rarely, and never silently.

This record deliberately does not relax anything about the **load model**, about
`Spark.Nodes.Core` being forbidden to reference `Spark.Engine`, or about `Spark.Api` staying
small. Those three were argued on their own grounds and none of them depended on publishing.
