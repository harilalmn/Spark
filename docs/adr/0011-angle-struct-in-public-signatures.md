# ADR-0011 — An `Angle` struct in every public angular signature; radians internally

**Status:** Accepted
**Date:** 2026-08-27
**Deciders:** Nicety

## Context

Angles are the classic silent-failure parameter in a geometry API: `Rotate(plane, 45)` and
`Rotate(plane, 0.7853981634)` both compile, one of them is wrong, and nothing tells the author
which. Kernels conventionally solve this by documenting radians and moving on.

Spark has a second, sharper reason to care, and it is the one that decides the matter. Nodes
are generated by reflection over public members, including members of third-party packages the
author of Spark has never seen. The node generator's only information about a parameter is its
`Type`, its name and its XML doc comment. If an angular parameter is a `double`, the generator
cannot distinguish it from a length, a scale factor or a count — so either every angular port
in the product is in radians, which no AEC user wants, or there is a hand-maintained table
saying which parameters are angles. That table is the `DocGenerator` failure shape: a
string-keyed map between code and metadata, which drifts silently and needs its own test suite
to notice.

## Decision

A `readonly struct Angle` appears in **every** public angular signature across
`Spark.Geometry`, `Spark.Api` and `Spark.Nodes.Core`. It stores radians internally and is
constructed explicitly — `Angle.FromDegrees(45)`, `Angle.FromRadians(x)`. There is **no
implicit conversion from `double`**.

The node generator treats `Angle` as a typed hook: an `Angle` parameter automatically renders
as a degree-valued port, for first-party and third-party libraries alike, with no attribute and
no table.

## Alternatives considered

### Bare `double` in radians

What almost every geometry kernel does, and defensibly: zero wrapper, zero conversion, no new
type for users to learn, and the value is already in the form every trigonometric function
wants. It lost because the node generator has nothing to key on. Every angular port would show
radians, or the degree behaviour would come from a maintained list of parameter names, which is
precisely the drift-prone mechanism this project has already been burned by.

### Bare `double` in degrees at the API surface

Friendlier to the AEC audience that D9 prioritises, and it makes the node ports right by
default. It lost because internal code then converts on every call, and the first time someone
writes `Math.Sin(angle)` against an unconverted degree value the bug is silent and plausible.
It also makes the public API disagree with every other geometry library a user might call from
a code block.

### `Angle` with an implicit conversion from `double`

The pragmatic middle: the typed hook still works, existing code and examples still compile, and
nobody has to write `Angle.FromDegrees`. It lost because it reintroduces exactly the ambiguity
the type exists to eliminate. `Rotate(plane, 0.5)` would compile, and the reader would have no
way to know whether the author meant half a radian or half a degree. A type that can be bypassed
by accident provides documentation, not safety.

## Consequences

### Positive

Angular ports are degree-valued everywhere by construction, including in packages whose authors
have never heard of Spark, provided they use the type. Unit confusion at the API boundary
becomes a compile error rather than a wrong model. The type is a natural home for normalisation,
wrapping and the degree/radian formatting the UI needs.

### Negative

Every angular call site is more verbose: `Arc.ByCentrePlaneRadiusAngle(p, r, Angle.FromDegrees(90))`
rather than a bare number. Third-party libraries that use bare `double`s — which is most of
them — get radian-valued ports until they adopt `Angle`, so the benefit is asymmetric and Spark
cannot fix it on their behalf without the table this decision rejects. The struct also has to be
written carefully for hot loops: `readonly struct`, `in` parameters, and no incidental boxing
through any interface.

### Neutral

`Angle` sits alongside `Tolerance` (ADR-0010) as the second value type whose presence in a
signature carries meaning to the tooling rather than only to the reader. That pattern is worth
noticing but should not be over-applied — a type per unit is not the goal.

## Notes

If a third-party library's radian ports become a common complaint, the tempting fix is a
per-parameter override table. That is the `DocGenerator` anti-pattern and should be refused; a
better answer would be an opt-in attribute the library author applies, keeping the mapping in
the library that owns the parameter rather than in ours.
